# UI architecture

Phase 2 covers two user surfaces: the GTK desktop app and the public
website. Both talk to the *same* runtime state - nothing here is a static
mockup.

## Desktop (`crates/keyvibes-ui`)

```
keyvibes run  ──engine──►  unix socket $XDG_RUNTIME_DIR/keyvibes/control.sock
                              │  newline-delimited JSON (kv-control)
                              ▼
                        keyvibes-ui (GTK4 + libadwaita)
```

- **Transport.** `session.rs` owns one `kv_control::Client`. It connects
  (50 ms poll, 20 s bind timeout), optionally `Subscribe`s, and reconnects
  after 300 ms if the engine goes away. Requests are answered on the GTK
  main loop through an unbounded `async_channel`; a blocking call is never
  made on the UI thread.
- **State.** Every reply carrying a snapshot lands in `App::state` and is
  rendered by `App::render()` behind a `suppress` flag, so a programmatic
  update never echoes back as a user edit. A 2 s `GetState` tick keeps
  counters, peak and diagnostics moving while nothing is being changed.
- **Controls.** Each widget posts exactly one protocol request
  (`SetEnabled`, `SetVolume`, `SetVariation`, `SetSpatial`,
  `SetReleaseSounds`, `SetPack`, `Preview`). The engine applies them
  lock-free on the control thread and queues a config save, so the widget
  you see is always the state the engine confirmed - the UI never writes
  `config.toml` itself.
- **Persistence.** The engine owns `~/.config/keyvibes/config.toml`
  (`version`, `enabled`, `pack`, `volume`, the three toggles). The UI only
  ever asks the engine to change something; a save failure is reported back
  through the reply and surfaced as a toast, so the user is told when a
  change did not stick.
- **Pack switching.** `SetPack { selector }` reloads the pack on the
  engine's main loop (never in the audio callback), the reply carries the
  new `State`, and a toast confirms the switch. Preview plays a few keys
  through the real output path via `Preview`.
- **Status and errors.** The stage has three states - `starting`
  (spinner), `error` (message + "Try again" reruns the same boot path),
  `main`. On top of the pages sits the issues banner fed by
  `State.issues`, which the engine fills with conditions that need the
  user (audio stream errors, no readable keyboard, silent presses from an
  incomplete pack). Anything transient goes through `ToastOverlay`;
  anything actionable ("which group, which fix") is repeated by the
  read-only Diagnostics checks on the System page, each with a copyable
  fix command.
- **Real-time safety.** Nothing in this crate touches the audio callback.
  The callback only consumes lock-free atomics the control thread stores;
  pack swaps, socket reads, logging and allocation all happen elsewhere.
- **Screen capture.** `KEYVIBES_SCREENSHOT=/path.png` (optional
  `KEYVIBES_SCREENSHOT_PAGE=sounds|audio|system`) makes the window render
  itself through GSK and quit, so documentation screenshots come from the
  real widgets.

## Website (`site/`)

Static, no build step, no runtime dependency on the engine.

- `index.html` / `download.html` / `assets/styles.css` / `assets/app.js`
  are hand-written and served as-is (GitHub Pages or any static host).
- `site/releases.json` is generated by `cargo xtask dist` and is the single
  source for the version string and every download link
  (`…/releases/latest/download/<exact filename>`).
- `site/packs.json` plus `site/assets/audio/*.wav` are generated by
  `cargo xtask site` straight from the installed `.kvpack` files: pack
  metadata (name, category, coverage, release support, author, licence,
  source), a slug, and one preview strip per pack. Each strip is the pack's
  own PCM for 26 press keys (Q through M, plus a release slot when the pack
  has release sounds) written straight to WAV, with the slot offsets in
  seconds recorded in the JSON. Keys the pack does not cover are simply
  absent from the strip.
- The soundpack section filters on that JSON, previews through
  `AudioBufferSourceNode` at the recorded offsets, and the hero keyboard
  plays the selected pack's own clips. No WebAudio synthesis stands in for
  a pack: if a clip is missing, the key stays silent and the UI says so.

## Verification

```sh
cargo xtask site                      # regenerate packs.json + previews
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
```

CI's `site` job checks that every local link resolves, then validates the
catalog itself: unique slugs and names, categories from the real set,
coverage within 1-104, release flags consistent with release key counts,
and a preview file per pack whose slots sit inside the strip (and no
release slot on a pack that has no release support).

The strips are checked for real audio outside CI: load the page, pick a
pack, press a key, and `window.__keyvibes.decoded` must report a decoded
`AudioBuffer` whose sample data is non-zero.
